3. Map Keycloak client roles to Spring Security authorities
Create a new configuration class:

Use the following implementation.
package com.store.order.config;

import org.springframework.core.convert.converter.Converter;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.server.resource.authentication.JwtGrantedAuthoritiesConverter;

import java.util.ArrayList;
import java.util.Collection;
import java.util.List;
import java.util.Map;

public class JwtRoleConverter
implements Converter<Jwt, Collection<GrantedAuthority>> {

private final JwtGrantedAuthoritiesConverter scopesConverter =
new JwtGrantedAuthoritiesConverter();

@Override
public Collection<GrantedAuthority> convert(Jwt jwt) {

Collection<GrantedAuthority> authorities =
new ArrayList<>(scopesConverter.convert(jwt));

Map<String, Object> resourceAccess =
jwt.getClaim("resource_access");

if (resourceAccess == null) {
return authorities;
}

Object clientAccess = resourceAccess.get("order-service");

if (!(clientAccess instanceof Map<?, ?> clientDetails)) {
return authorities;
}

Object rolesObject = clientDetails.get("roles");

if (!(rolesObject instanceof Collection<?> roles)) {
return authorities;
}

for (Object role : roles) {
if (role instanceof String roleName) {
authorities.add(
new SimpleGrantedAuthority("ROLE_" + roleName)
);
}
}

return authorities;
}
}
How does this converter work?
Suppose the JWT contains:
{
"resource_access": {
"order-service": {
"roles": [
"orders.read"
]
}
}
}
The converter reads the client roles and transforms them into Spring Security authorities.
The result is:
ROLE_orders.read
It also preserves the default scope authorities, such as SCOPE_profile, if present.
Important: This converter deliberately reads roles belonging to order-service. If you later create a dedicated client to call the Order Service, update the design so that the token's intended audience and the correct calling client's permissions are enforced.

package com.store.order.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.oauth2.core.DelegatingOAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2Error;
import org.springframework.security.oauth2.core.OAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2TokenValidatorResult;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.jwt.JwtDecoder;
import org.springframework.security.oauth2.jwt.JwtValidators;
import org.springframework.security.oauth2.jwt.NimbusJwtDecoder;

@Configuration
public class JwtAudienceConfig {

private static final String ISSUER =
"http://localhost:8080/realms/ecommerce";

private static final String REQUIRED_AUDIENCE =
"order-service";

@Bean
public JwtDecoder jwtDecoder() {

NimbusJwtDecoder decoder =
NimbusJwtDecoder.withIssuerLocation(ISSUER).build();

OAuth2TokenValidator<Jwt> issuerAndTimestampValidator =
JwtValidators.createDefaultWithIssuer(ISSUER);

OAuth2TokenValidator<Jwt> audienceValidator = jwt -> {
if (jwt.getAudience().contains(REQUIRED_AUDIENCE)) {
return OAuth2TokenValidatorResult.success();
}

OAuth2Error error = new OAuth2Error(
"invalid_token",
"The required audience is missing: "
+ REQUIRED_AUDIENCE,
null
);

return OAuth2TokenValidatorResult.failure(error);
};

decoder.setJwtValidator(
new DelegatingOAuth2TokenValidator<>(
issuerAndTimestampValidator,
audienceValidator
)
);

return decoder;
}
}
Change ISSUER if your Keycloak realm uses a different URL.
How this works
The decoder now validates three things:
Issuer: The token comes from your expected Keycloak realm.
Timestamp: The token is within its valid time window.
Audience: The token contains order-service in its aud claim.
If the token is otherwise valid but has the wrong audience, authentication fails and the API returns 401 Unauthorized.
You do not need to change your existing SecurityConfig.java. It already configures JWT authentication, and Spring Security will use this JwtDecoder bean.
Your existing JwtRoleConverter continues to map the orders.read role.

The scope and role happen to describe similar permissions in this example, but they are separate claims with separate configuration. Keycloak does not automatically make one a collection of the other.
3. Why do we need both roles and scopes?
You don't necessarily need both. You can choose an authorization approach that fits your application.
For example, your current Order Service checks this:
.hasAuthority("ROLE_orders.read")
Your custom JwtRoleConverter extracts the Keycloak role and converts it to that Spring Security authority.
If you instead decide to authorize using OAuth2 scopes, you could check:
.hasAuthority("SCOPE_orders:read")
Spring Security normally creates SCOPE_... authorities from the token's scope claim.
Both approaches can protect endpoints. Using both is useful only when you deliberately want to enforce both kinds of restrictions.

2. How can Spring Boot use them?
Suppose you want to allow access only when the token has the inventory:read scope.
.requestMatchers(HttpMethod.GET, "/inventory")
.hasAuthority("SCOPE_inventory:read")

.requestMatchers("/inventory/**")
.hasAuthority("ROLE_inventory-manager")

3. What if you require both?
You can require both conditions:
.requestMatchers(HttpMethod.GET, "/inventory")
.access((authentication, context) -> {
var authorities = authentication.get().getAuthorities();

boolean hasReadScope = authorities.stream()
.anyMatch(a -> a.getAuthority()
.equals("SCOPE_inventory:read"));

boolean hasManagerRole = authorities.stream()
.anyMatch(a -> a.getAuthority()
.equals("ROLE_inventory-manager"));

return new AuthorizationDecision(
hasReadScope && hasManagerRole
);
})
This allows the request only when the token has both the required scope and the required role. This example assumes your JWT converter extracts both claims.
4. Remember the three distinct concepts
Audience: Which API is the token intended for?
Scope: What OAuth2 access has been granted?
Role: What role or permission assignment does the identity have?
For example, a token could target inventory-service, have scope inventory:read, and carry the role inventory-manager. Those values do not need to match.
One important detail: OAuth2 does not mandate that every scope describe a permission, nor that every role describe a job title. These are common design conventions; your application defines the actual authorization rules.

Step 4.1 — JWT Access Token Expiration in Spring Boot
Let's understand what happens internally when a JWT expires, using your existing Keycloak + Order Service + Inventory Service implementation.
We'll first understand incoming tokens, which protect your APIs. Then we'll look at outgoing tokens, which Order Service uses to call Inventory Service.
1. What is an access token's expiration?
When Keycloak issues a JWT, it includes an exp claim that specifies when the token expires.
For example, a simplified JWT payload might look like this:
{
"iss": "http://localhost:8080/realms/ecommerce",
"aud": ["order-service"],
"exp": 1793300000,
"resource_access": {
"order-service": {
"roles": ["orders.read"]
}
}
}
The important claim here is:
"exp": 1793300000
This is a Unix timestamp representing the token's expiration time.
After that time, the token is expired and should no longer be accepted.
Why do tokens expire?
Imagine a token never expired. If someone stole it, they could continue using it until it was explicitly revoked or another validation mechanism rejected it.
Short-lived access tokens limit the period during which a stolen token can be used.
For example, suppose Keycloak issues a token that expires after five minutes:

| Time | Token status |
| --- | --- |
| 10:00 | Token issued |
| 10:02 | Valid |
| 10:04 | Valid |
| 10:05 | Expired |
| 10:06 | Must not be accepted |

The five-minute duration is just an example; your actual token lifespan depends on your Keycloak configuration.
